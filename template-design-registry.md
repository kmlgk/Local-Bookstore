### Header component changelog (applies to all pages in this template)
The header went through two corrective revisions after initial launch — noted here so future templates don't repeat the same mistakes:
1. **Grid → Flex:** original header used `grid-cols-3` (three *equal* thirds: left-nav / centered-logo / right-nav+controls). Equal-thirds tracks don't grow to fit content — the right column (nav + icons + CTA) needed far more than 1/3 of the header width at realistic desktop sizes, overflowing and visually overlapping the centered logo. Replaced with a single flex row (logo `shrink-0` + nav `flex-1` + controls `shrink-0`) sized by actual content, not arbitrary fractions.
2. **Breakpoint lg → xl:** even the corrected flex layout was razor-thin at 1024px (`lg`) with 6 nav links; adding a 7th link (Home 2) would have overflowed again. Desktop nav/CTA now gate on `xl` (1280px) instead of `lg` (1024px) — tablet-landscape widths (1024–1279px) now correctly get the hamburger drawer instead of a cramped nav row. `DESKTOP_BREAKPOINT` in `main.js` was updated to match (1280).
Also fixed: the header's transparent-over-hero state (home page only) was replaced with a permanent semi-opaque glass background on every page, since dark nav text over a busy/dark hero photo was unreadable; and the mobile drawer's RTL "closed" position (`translateX(-100%)`) was removed entirely because it wasn't matched by an equal flip of the drawer's physical docking side (`right-0`), which pulled the panel partially into view the instant RTL was toggled — the drawer now always docks and slides from the right regardless of direction.

### Gallery Page redesign (`gallery.html`)
Redesigned after initial launch — replaced the original asymmetric "editorial" grid (one `col-span-2 row-span-2` featured tile + one `col-span-2 aspect-video` tile among plain squares) with a **uniform grid**: every tile is the same `aspect-[4/5]`, so the CSS grid auto-flow can never leave a gap or an incomplete row, in any filtered state, at any breakpoint. The asymmetric layout was the root cause of the original imbalance — with irregular tile spans, categories couldn't be filtered to an even, gap-free layout no matter how many photos each had.
- **Photo count:** Every category now holds exactly **4 photos** (16 total, was 4/3/3/2 unevenly). 4 new content-verified images were sourced via Unsplash search (not guessed IDs) to fill the gaps: one playground photo, one art-activity photo, two meal-time photos.
- **Filter tabs:** Each tab now shows a live photo count badge (`data-filter-count`, computed from the DOM at runtime, not hardcoded) — e.g. "Meals ⸱" — plus a category icon. Active tab styled via a new `.gallery-filter-btn[aria-selected="true"]` state (coral fill + bottom-shadow, distinct from the `tab-btn` class used for the age-group tabs elsewhere).
- **Category badge chips:** Each tile carries a small always-visible color-coded pill top-left (sky=Classroom, leaf=Playground, coral=Activity, sunshine=Meal Time) so the category reads at a glance even before hovering — new pattern, not used elsewhere in the template.
- **Load More pagination:** `data-gallery-grid` + `data-batch-size="8"` drive a JS batching system (`initGalleryFilter` in `main.js`, rewritten): "All Photos" shows 8 initially with a "Load More Photos" button revealing the rest; switching to any single-category filter shows all 4 of that category directly (no pagination needed for a set that small) and hides the Load More button; returning to "All Photos" resets the batch. A live `data-gallery-count` label ("Showing 8 of 16 photos") tracks the current state.
- **Reveal animation:** New `.gallery-tile` / `.gallery-tile-visible` CSS pair (opacity + translateY + scale transition) replaces the old instant `display:none` toggle — items entering view (via filter change or Load More) now fade/rise in smoothly instead of popping. Deliberately *not* wired through GSAP ScrollTrigger's `data-reveal` system, since ScrollTrigger initializes against an element's layout box at scan time and this grid's items are frequently `display:none` at load (everything past batch 1) — mixing the two would have produced unreliable trigger positions.

**Gallery page content expansion** (second pass, same file): the page went from "hero + filter grid + one-line CTA" to a full campus-life showcase. ### Header, mobile-menu & lightbox changelog (fixes applied after initial launch)
Three corrective revisions, recorded so future templates don't repeat the same mistakes:
1. **Split-nav → logo-left:** the original "centered-logo, split-nav-either-side" header was replaced with a conventional logo-left / centered-nav-links / right-controls layout, at explicit user request. Logo position is now identical on mobile and desktop (far left) rather than centering only on desktop and left-aligning only on mobile.
2. **Nav-link centering:** the centered nav-links group was initially left-aligned immediately after the logo (`flex-1` container, links packed to its start); changed to `justify-center` so the links center within the space between the logo and the right-side controls, per explicit request.
3. **GLightbox blank popup:** gallery images hosted on Unsplash have no file extension in the URL (`?auto=format&fit=crop&w=1400&q=80`), so GLightbox couldn't auto-detect them as images and rendered an empty iframe on click. Fix: every `.glightbox` anchor's `data-glightbox` attribute must include an explicit `; type: image` (e.g. `data-glightbox="title: Nursery Room; type: image"`) whenever the image URL lacks a recognizable extension.
4. **RTL skip-link scroll-width explosion:** the accessibility skip-link used the classic `left: -9999px` off-screen-hiding technique. Under `dir="rtl"`, the browser's overflow/scrollWidth calculation folds that huge negative offset into `document.scrollWidth` (observed: exactly `9999 + viewport-width`), which pushed the entire visible viewport off to a blank stretch of the inflated canvas — the whole page (not just the skip-link) appeared to render blank whenever RTL was toggled with the mobile menu open. Fix: hide the skip-link with `transform: translateY(-100%)` instead of a large negative `left` offset — no large offsets anywhere means nothing for RTL's overflow recalculation to inflate. **Lesson for future templates: never use `left: -9999px` (or any large fixed-pixel physical offset) for visually-hidden-until-focused elements on a template that supports RTL — use a transform-based hide instead.**
5. **Dropdown click-vs-hover race:** an early version of the desktop "Home" dropdown toggled open/closed on click while *also* opening on `mouseenter` / closing on `mouseleave`. A mouse user hovering (opens it) then clicking (toggle → closes it) got a dropdown that closed on click. Fix: click now always calls `open()` (never toggles), and closing is delegated entirely to `mouseleave`, outside-click, `focusout`, and Escape — click and hover no longer fight each other.
6. **Hero decorative shapes bleeding through the translucent header:** two of `index.html`'s floating cloud/star SVGs sat at `top-16`/`top-24` relative to the hero section — but since the header is `position: fixed` (removed from document flow), the hero section's own top edge is at document y=0, not below the header. At `lg`+ widths those shapes rendered underneath the header's `bg-white/95 backdrop-blur-md`, faintly bleeding through as a ghost artifact only visible on close inspection. Fix: pushed both shapes further down (`top-16`→`top-32`, `top-24`→`top-36`) to clear the header's ~92–104px height with margin. **Lesson: any absolutely-positioned decorative element inside the first section after a `position: fixed` header needs a `top` offset comfortably larger than the header's total height, since the section's own coordinate origin starts at the true document top, not visually below the header.**
7. **Mobile drawer content pinned to one edge at tablet widths:** per an explicit requirement the overlay itself must stay 100% width at every breakpoint, but the nav content inside it was `items-end`/`text-right` unconditionally — great on a 320–425px phone, but at 768–1279px (tablet, still below the `xl` hamburger cutoff) it left the content pinned to the far right of a mostly-empty full-width canvas. Fix: `items-end sm:items-center` + `text-right sm:text-center` (nav, the Home-submenu wrapper, and its panel) — right-aligned on phone widths, centered from `sm` (640px) up, while the overlay itself never stops being 100% width. Both requirements ("100% width" and "properly aligned on tablet") are satisfied simultaneously because they're about content alignment vs. container width — not the same property.
8. **`gallery.html` missing GSAP/ScrollTrigger includes:** the original gallery page never used scroll-reveal animation, so it never loaded the GSAP/ScrollTrigger `<script>` tags every other page includes. When later content sections were added using the site's standard `data-reveal` / `data-reveal-number` attributes, `initScrollReveals()` silently no-op'd (`typeof gsap === 'undefined'` guard) — the new sections just appeared statically (harmless) but the animated stat counters stayed frozen at their literal `0` fallback text forever (not harmless — a visibly broken counter). Fix: added the two missing script tags. **Lesson: `data-reveal*` attributes are inert markup, not a self-contained feature — always confirm the GSAP/ScrollTrigger scripts are actually present on a page before using them, especially when extending a page that predates the site's animation system.**
9. **Confirmed a genuine image/caption mismatch, and found a reliable way to catch more:** `about.html`'s new Learning Approach section used `photo-1497633762265-9d179a990aa6` captioned "Teacher guiding preschoolers through a hands-on classroom lesson" — an ID picked from memory very early in this project, before the site adopted Unsplash-search-then-verify sourcing. The rendered photo was actually a stack of colored books. Caught it by eye in a full-page review screenshot, not by any automated check (HTTP 200 + a WebFetch text description of the *search results page* both said nothing about the *actual photo's contents*). **Working technique discovered while fixing this: `WebFetch` can't describe an image URL directly (it only sees encoded binary and says so) — but it silently saves that binary to a local `.jpg` in the tool-results folder every time, and the `Read` tool *can* view that saved file. So `WebFetch` on the raw `images.unsplash.com/photo-…` URL (any prompt) → `Read` on the path it reports saving to, is a real way to visually verify a specific candidate image before committing to it, not just trust its alt-text search description.** Replaced with `photo-1761208662734-fb46f1398551`, verified this way before use. Apply this fetch-then-Read check to any image sourced from memory or from a search-results description rather than viewed directly — search descriptions describe the search snippet, not necessarily what's in the full-resolution photo.

10. **LTR mobile/tablet hamburger-left fix regressed RTL:** to move the hamburger to the left / logo to the right on mobile/tablet in LTR, the previous fix removed the hamburger's old unconditional `ml-auto` and replaced it with `ltr:order-1` / `ltr:order-2 ltr:ml-auto` (scoped only to `dir="ltr"`). This fixed LTR but left RTL with *no* edge-anchoring at all below `xl`: both elements defaulted to `order: 0` and sat packed together at the flex-start side (visually the right, since RTL mirrors `flex-direction: row`), leaving a large dead gap on the opposite side — exactly the bug in the reported screenshot. **Fix: added `justify-between` to the header's main flex row** (`<div class="flex items-center gap-4">` → `...justify-between gap-4`). This is direction-agnostic — `justify-content: space-between` always anchors the first and last flex-order items to the start/end edges, and "start/end" already flip correctly with `dir` on their own. Combined with the existing `ltr:order-1`/`ltr:order-2` swap (which only needs to override *which* element is first/last, not push anything to an edge), both directions now anchor correctly with no extra `ltr:`/`rtl:` duplication needed for the edge-pinning itself. At `xl`+ this has no effect, since the `flex-1` nav already consumes all free space regardless of `justify-content`. **Lesson: when reversing a two-element edge-pinned layout for only one text direction, prefer `justify-between` (inherently bidi-correct) over an `auto`-margin scoped to a single `dir:` variant — a scoped auto-margin fixes the direction you tested and silently strips the other direction's spacing if it was relying on that same margin before.**

### Content-accuracy note (image sourcing)
An initial pass populated photo placeholders with Unsplash `photo-<id>` URLs recalled from memory and verified only by HTTP 200 status — several turned out to depict unrelated subjects once rendered (a library interior captioned "Pre-K Classroom," a magnifying glass on a laptop captioned "Story Time," a street-photography shot in a gallery grid). HTTP 200 confirms a URL *resolves*, not that its *content* matches the caption. The fix: use `WebFetch` on Unsplash search-results pages (e.g. `unsplash.com/s/photos/preschool-classroom`) to extract real `images.unsplash.com/photo-…` URLs paired with their actual alt-text descriptions, then verify those specific URLs return 200 — only then treat an image as content-verified. Every photo in this template was re-sourced this way. Apply this method from the start on future templates rather than as a corrective pass.

### Cross-page image de-duplication pass
A full-site audit found the same photo reused across 2–5 *different* pages for entirely different sections — e.g. one "art studio" photo appeared on `index.html`, `home-2.html`, `about.html`, `gallery.html` (twice — once in the grid, once in its own Classroom Highlights section), and `teachers.html` simultaneously. - **Teacher/staff headshots are the deliberate exception** — the same person's photo is *supposed* to recur across their bio card, the shared teacher-modal, and any homepage preview swiper; that's correct identity consistency, not a duplication bug, and was left untouched.

### Horizontal scroll strips unusable with a desktop mouse
Several sections (`index.html`'s facility gallery preview, `home-2.html`'s daily-activities strip, `about.html`'s milestones timeline, `gallery.html`'s testimonial strip) use `overflow-x-auto no-scrollbar` — deliberately hiding the scrollbar for a cleaner look. This left desktop mouse users with **no way to reach the overflow content at all**: a mouse only produces a vertical wheel delta, which just scrolls the *page* past the section, and there's no visible scrollbar to drag since it's hidden by design. Touch and trackpad users never noticed since horizontal swipe gestures work natively. Confirmed via a Playwright test *before* fixing: `scrollWidth` (1424px) genuinely exceeded `clientWidth` (1280px) — extra content existed and was permanently unreachable by mouse.
- **Fix, centralized in `main.js`/`style.css` rather than per-page** (`initHorizontalScrollStrips()`, applied via the generic `.overflow-x-auto.no-scrollbar` selector so it automatically covers every current and future strip using this pattern, no per-page wiring needed): a `wheel` listener redirects vertical wheel delta into `scrollLeft` and calls `preventDefault()` so the page itself stops scrolling while hovering a strip with room left to scroll; a `mousedown`/`mousemove`/`mouseup` set adds click-and-drag scrolling (`cursor: grab` → `grabbing` via a `.is-dragging` class, which also sets `pointer-events: none` on children mid-drag so a card's own hover/link states don't fight the drag); a `moved` flag suppresses the trailing `click` event after an actual drag so dragging a strip never accidentally activates a link/card underneath the cursor, while a plain (non-drag) click still navigates normally.
- **Lesson: `overflow-x-auto` + `no-scrollbar` is a mobile-first pattern that silently fails for desktop mouse users** — if a horizontal-scroll strip needs a hidden scrollbar for visual cleanliness, it needs the wheel-redirect + drag-to-scroll pair (or explicit prev/next buttons) from the start, not just on mobile where native swipe already works. Apply `initHorizontalScrollStrips()`'s selector-based approach on future templates too, since it fixes every matching strip site-wide with zero per-instance markup changes.

- **Caught and fixed during this pass, not after:** two storefront/exterior photos initially chosen for the About and Contact page heroes turned out to prominently display a *different*, real business's signage ("Riverside Market," "Mercadona") baked into the photo. Since the brand in this template is "GreenCart Market," a hero photo with a competing store name reads as a visible content-accuracy defect, not just a stylistic mismatch. Both were swapped — About's hero to an unbranded aisle/produce-display photo, Contact's hero to an unbranded checkout-counter photo — before the pages were ever marked complete. **Lesson for future templates: real estate/storefront stock photography frequently has another business's actual name or logo legible in the shot — treat any photo with readable third-party signage as unusable for a hero/banner on a fictional-brand page, the same way a caption/content mismatch would be treated, and check for it specifically since it won't show up in a simple "does this photo depict a grocery store" content check.**

### Testing & functional-bug changelog (found and fixed via headless-Chrome + Puppeteer interaction testing before sign-off)
Unlike T1/T2 (whose changelogs record fixes made after user reports), this template was interaction-tested end-to-end — dark/light toggle, RTL/LTR toggle, header search, mobile bottom-sheet, category filters, steppers, all three forms, FAQ accordion, and horizontal-overflow checks at 320/375/425/768/1024/1280/1440px on every page — **before** being marked complete, using headless Chrome (`--headless=new --screenshot`) for visual review and a Puppeteer-core driver (pointed at the system Chrome install) for scripted interaction. Three real bugs were caught this way and are recorded here so future templates can watch for the same classes of mistake:
1. **`data-reveal="left"/"right"` scroll-reveal transforms caused permanent horizontal overflow on every page.** The reveal system's initial (pre-intersection) state applies `transform: translateX(±32px)` so elements slide into place. Since this transform is applied to *every* matching element on page load — including ones far below the fold — any element whose untransformed position was already near the left/right edge of the viewport pushed the document's scrollable area past the viewport width from the very first paint, before any scrolling or JS observer had fired. This produced a consistent 8–19px `scrollWidth > clientWidth` overflow at *every* breakpoint on *every* page, confirmed via `document.documentElement.scrollWidth - clientWidth` in a scripted check. **Fix: `overflow-x: hidden` on `html, body`** — this is the standard, defensive counter-measure for exactly this class of bug (any decorative/animation transform that might transiently or permanently extend layout bounds) and was verified to bring overflow to exactly 0px at all 7 tested widths across all 8 pages afterward. **Lesson: any template using transform-based entrance animations (translateX/Y reveal, floating decorative shapes, etc.) needs a global `overflow-x: hidden` safety net, not just careful placement of individual elements — CSS transforms on far-below-fold elements can silently extend `document.scrollWidth` before the user ever scrolls there or the animation resolves.**
2. **Header search overlay had no results container in the markup.** The JS (`initHeaderSearch` → `renderResults`) was written against a `[data-search-results]` selector that was never actually added to the header HTML on any page — the search input and close button existed, but typing produced no visible output at all (a silently-dead feature, not a crash). Caught by a scripted test that typed "milk" and asserted at least one result rendered; it returned zero. **Fix:** added an absolutely-positioned `[data-search-results]` dropdown panel (rounded, bordered, scrollable) as a sibling of the input inside the now-`relative` search-overlay container, on all 7 pages that include the header search. **Lesson: when JS is written against a `data-*` hook, grep the HTML to confirm that hook actually exists before considering the feature done — a missing container fails silently (no console error) rather than loudly.**
3. **Success messages were nested inside the `<form>` they belonged to, so hiding the form on submit also hid its own success message.** The submit handlers in `main.js` (`initForms`, `initBulkOrderForm`) add a `hidden` class to the `<form>` element itself and simultaneously try to reveal a `[data-form-success]` message — but on the general contact form and the bulk-order form, that success `<p>` was a *child* of the form being hidden, so `display: none` on the parent made the success message unconditionally invisible regardless of its own class state. (The two newsletter forms were unaffected — their success message happened to already be written as a sibling *after* `</form>`, which is what exposed the inconsistency.) Caught by a scripted test that submitted valid data and asserted the success message's computed visibility, not just its class list. **Fix:** restructured both affected forms so `[data-form-success]` is a sibling of `<form>` (wrapped in a shared parent `<div>` where needed to preserve grid layout), and updated `main.js` to look up the success element via `form.parentElement.querySelector('[data-form-success]')` instead of `form.querySelector(...)`. **Lesson: never place a "success" confirmation message as a descendant of the form element you plan to hide on success — verify the fix by checking actual rendered visibility (e.g. `!el.classList.contains('hidden')` *and* the element is reachable), not just that the class-toggle code ran without throwing.**

**Bugs caught during this pass (scripted-test + visual-review, before sign-off):**
1. **FAQ search had a one-way "ratchet" bug that permanently mis-expanded accordion items.** `page.type()`-style character-by-character input fires an `input` event per keystroke; the original handler set `aria-expanded="true"` on any item matching the *current partial* query but never set it back to `false` when a later, more specific keystroke stopped matching it. Typing "delivery" letter-by-letter (d → de → del → …) transiently matched nearly every FAQ item (most contain the letter "d" somewhere) and force-expanded all of them; by the time the full word landed only 3 items were *visible*, but all ~13 remained `aria-expanded="true"` underneath — confirmed by a scripted check (`TRUE_AFTER_DELIVERY_SEARCH: 13` before the fix). **Fix:** the expand/collapse line changed from `if (match && q) { …aria-expanded, 'true' }` (write-only) to `if (q) { …aria-expanded, match ? 'true' : 'false' }` (always reconciles both directions whenever a query is active). **Lesson: any "auto-expand on search match" feature that fires per-keystroke must also explicitly *un*-expand non-matches on every keystroke, not just expand matches — otherwise state from an earlier, broader partial-query accumulates and never clears.**

### Global policy update — strict image uniqueness, and second premium redesign pass (Home 1, Home 2, Categories, About)
The client issued a standing, template-wide requirement after the first premium-redesign pass: **no image may ever be reused anywhere on the site, even for the same product/category appearing on multiple pages.** This is stricter than the "2-page reuse of a genuinely on-topic photo is acceptable" precedent recorded earlier in this file (T2's registry) — that precedent is superseded *for this template going forward*. Apply the strict no-reuse rule from the start on any future template revision, rather than as a retrofit.

**Audit method (repeatable for future passes):** extract every `images.unsplash.com` / `plus.unsplash.com` URL from every HTML file with a `grep -ohE` sweep, strip query-string noise (`?w=`, `&q=`), `sort | uniq -c`, and any count greater than 1 is a duplicate needing a replacement for every occurrence past the first. This template had **94 total image usages across 8 pages, of which 27 distinct photo IDs were each reused 2–5 times — 46 individual occurrences needed a fresh, unique replacement.** For each duplicate group, one occurrence was designated the "keeper" (kept unchanged) and every other occurrence got a newly-sourced photo, with accurate new `alt` text written to match what the replacement image actually shows (not left describing the old photo). After all replacements, the same audit command must return zero output, and a bulk `xargs -P N curl -o /dev/null -w '%{http_code}'` sweep over every unique URL must show 100% `200`.

**New rejects found while sourcing ~40 replacement photos** (beyond the watermark/404 lessons already recorded above):
- Several "clean-sounding" bakery/pantry candidates turned out to have a competing real bakery's **branded packaging, signage, or a name/logo baked into the shot** once actually viewed (a "Josey Baker Bread"-branded paper bag; a wall-sized "Rocco Princi" bakery mural with "STARBUCKS RESERVE" watermarked into the corner; a hand-lettered German-language chalkboard sign with zero food visible). None of these were catchable from alt-text alone ("a bunch of breads that are on a rack" gave no hint of the branding baked into the frame) — only the fetch-then-Read visual check caught them, reinforcing the standing lesson that alt-text/search-snippet descriptions describe the search result, not full photo content.
- A bakery display-case candidate had **visible foreign-currency (€) price tags** baked into the shot ("Croissant 1.00€") — not a competing brand, but a content-accuracy mismatch for a USD-priced Ontario store; discarded for the same reason a mismatched caption would be.
- **Lesson reinforced at larger scale:** when sourcing many replacement photos quickly under time pressure, the failure mode shifts from "wrong subject" (the earlier T1/T2 lesson) to "right subject, wrong background details" — a photo can accurately show bread, croissants, or pantry jars and *still* be unusable because of an incidental price tag, chalkboard, or logo elsewhere in the frame. Bakery and prepared-food-display photography is disproportionately likely to include this kind of incidental real-world signage compared to plain produce/product-on-a-surface shots — budget extra verification passes specifically for that category.

**Bugs caught during this pass (scripted-test + visual-review, before sign-off):**
1. **Tailwind's CDN-injected utility stylesheet silently defeated a custom display-toggle class due to cascade order, not specificity.** `.aisle-panel { display: none } .aisle-panel.is-active { display: grid }` looked correct and the `initAisleTabs()` JS was toggling `is-active` correctly (confirmed by inspecting `classList` directly) — but every panel remained visibly `display: grid` regardless, because each panel `<div>` also carried Tailwind's own `.grid` utility class for its internal layout, and the Tailwind CDN script injects its generated `<style>` block into `<head>` *after* `style.css` has already been parsed (it runs synchronously and appends at the point the script tag was declared, while `style.css` is a `<link>` earlier in the same `<head>`), so `.grid` — same specificity as `.aisle-panel`, later in source order — won the cascade. Caught by a Puppeteer test that read `getComputedStyle(panel).display` before any tab was ever clicked and found it was already `"grid"` for a non-active panel. **Fix:** raised the hidden-state selector's specificity instead of reordering markup or adding `!important` — `.aisle-panel:not(.is-active) { display: none }` (two-part specificity, `0,2,0`) reliably beats `.grid` (`0,1,0`) regardless of load order. **Lesson: any custom CSS class that toggles `display` on an element which *also* carries a Tailwind display-utility class (`.grid`, `.flex`, `.block`, etc.) for its internal layout is racing the Tailwind CDN script's injection timing — don't rely on source order or equal-specificity single-class selectors to win; use `:not(.state-class)` or an equivalent higher-specificity selector, not `!important`, on the hidden-state rule.** A `getComputedStyle` check on the *unclicked* default state (not just the post-interaction state) is now the standard test for any new show/hide toggle feature going forward.
2. **Passing `navigation: undefined` to the Swiper constructor threw `Cannot read properties of undefined (reading 'enabled')` on every page load**, even though the intent ("only enable custom navigation for swiper instances that actually have matching buttons") was reasonable. Swiper 11's internal param-merging does not tolerate an explicitly-`undefined` value the same way it tolerates the key being absent entirely. Because `idx` is a single mutable variable shared by every closure (not a fresh per-call binding), by the time that `setTimeout` actually fired 500ms later, `idx` had already been reassigned to `next`'s value — so the cleanup callback ran against the *new current* span instead of the *old departing* one, permanently stacking a leftover `is-waiting` class (`opacity: 0`) onto the span that was simultaneously carrying `is-current` (`opacity: 1`). Re-verified with the same multi-sample technique across 12 samples / 6 seconds / 3 full rotations on both Home 1 and Home 2: exactly one span visible at all times, correct word at each expected interval. **Lesson: any `setTimeout`/`setInterval` callback that closes over a shared, later-reassigned loop/state variable (`idx`) rather than a value captured fresh at invocation time is a latent bug even when it "looks fine" in a quick visual check — this class of bug is specifically inclined to hide from screenshot-based QA (which naturally tends to sample near page-load, before enough animation cycles have elapsed to surface it) and needs an explicit multi-sample-over-time test, not a single screenshot, to catch.**

### Sixth pass — template-wide container/header alignment re-audit, and a full "Trending This Week" rebuild (Home 1)

**Container/alignment re-audit — a testing-methodology lesson, not a template bug:** the first automated pass of this audit falsely flagged every content container on every page as misaligned (`leftMismatch`/`rightMismatch` > 0 everywhere). Root cause was in the *test script*, not the site: it compared each `.max-w-\[1440px\]` container's own unpadded `getBoundingClientRect().left` (which is legitimately `0` at the viewport's exact max-width, since the container itself has no left offset before its own `px-4`/`px-6` padding is applied) against the header **logo's** rendered position (which is *already* inset by the header's identical container's padding). Re-run with the fix across all 8 pages at 1024/1440/1920px: **zero mismatches everywhere** — the container system was already correct going into this pass; no site changes were needed here. **Lesson: when an automated geometry audit reports every single page as broken (100% failure rate on a system that passed manual/visual review repeatedly in prior passes), suspect the test's comparison logic before the site — a measurement bug that compares two different "kinds" of edge (padded vs. unpadded, content-box vs. border-box) produces exactly this kind of uniform false-positive across every page, whereas a real template regression would typically affect specific pages or sections inconsistently.**

1. **Nested a `<button>` inside an `<a>` in an early draft of the spotlight card** (to make the whole card a link to `categories.html#produce` *and* keep the "Add to list" button inside it). This is invalid HTML — a `<button>` is not permitted as a descendant of an `<a>`, and browsers silently "fix" the malformed markup via the HTML parser's adoption-agency algorithm, which can rearrange the DOM in ways that break event handling unpredictably. Because `overflow-x: hidden` on `html`/`body` (added in an earlier pass specifically to prevent this class of bug from producing a page-wide horizontal scrollbar) was doing its job, `document.documentElement.scrollWidth` reported **zero** overflow even while the spotlight card and list rows were visibly clipped mid-content on screen (the "Add to list" button and a price figure cut off at the viewport edge) — a real, visible defect that a naive `scrollWidth`-only overflow check would have completely missed. Re-verified: grid track now correctly sizes to 358px (matching its container) at 375/390px widths, with zero overflow at both the element level and the document level, and correct behavior confirmed right at the `lg:` (1024px) breakpoint boundary from both sides (1023px and 1024px). **Lesson: `document.documentElement.scrollWidth <= clientWidth` is *not* sufficient proof that nothing is visually overflowing once a page has a global `overflow-x: hidden` safety net — that net converts a page-wide scrollbar bug into a silent content-clipping bug instead, which is arguably worse (invisible in the one check most likely to be run). Any new CSS Grid or Flexbox layout with fixed-size children (thumbnails, icons, buttons) sitting alongside a `flex-1`/shrinking text element needs `min-w-0` on the shrinking container(s) as a matter of course, and should be verified with an element-level `getBoundingClientRect()` check at the narrowest supported viewport, not just a document-level scrollbar check.**

The click handler only ever set the `aria-selected` *attribute* on filter buttons; the actual visual "active" styling is driven entirely by an `.is-active` *class* (`.category-chip.is-active { background: rgb(var(--color-primary)); ... }`). Since nothing in the click handler ever touched `.is-active`, clicking a filter button would correctly re-filter the cards but the *visual* active state would never move off the initially-hardcoded button — a real, dormant bug that had simply never been exercised end-to-end before. Caught by re-reading the JS function before reusing it for the new Categories filter bar (on the theory that anything about to be reused for the first time in a new context deserves a fresh read, not just a name-match assumption that it works), then confirmed with a scripted click-through test asserting `classList.contains('is-active')` after each filter click, not just checking that cards were hidden/shown correctly. **Fix:** the click handler now toggles `.is-active` alongside `aria-selected` on every button. **Lesson: a JS function that was written for a feature later removed before ever being visually exercised is not "known-working" just because it shipped without errors — re-verify it as if new the next time it's reused, especially checking that every piece of state the CSS depends on (classes) is actually being set, not just the accessibility attributes.**
2. **Two of three newly-sourced images for the Categories page's editorial tiles had real disqualifying content**, caught only by the fetch-then-Read visual-verification step (not by alt-text or search-result descriptions, which described both as clean): a "grocery haul" photo intended for "This Week's Bestsellers" had *five* different real, legible product brands baked into the packaging (Maple-brand syrup, Almond Breeze, Edgell corn, Milka chocolate, a "Higher Living" tea box); a farmer portrait intended for "Meet Our Local Farms" had a full tiled "Unsplash+" watermark repeated across the entire frame (a premium/Unsplash+ photo, despite the search listing not flagging it as such in the alt text). A third candidate for the same "Bestsellers" tile was also rejected after visual check for **visible foreign-currency crate price tags** ("330 K", "80 K" — matching the standing lesson about incidental signage in market-stall photography). **Fix:** all three were replaced with fetch-then-Read-verified clean alternatives before being committed to the page. **Lesson (reinforced, not new): this template's image-sourcing failure rate for "clean, unbranded, unwatermarked" candidates has consistently run at roughly 2-in-3 rejected across every pass that required fresh photos — budget for multiple rounds of visual verification as the default expectation, not the exception, especially for categories (grocery hauls, farmer portraits, market-stall shots) that have repeatedly produced contaminated results throughout this project's history.**
3. **The new hero trust-badge and testimonials-section avatar images were initially set to reuse the same 5 named-customer photos already used in the testimonial cards below** (e.g. Renata's and Priya's photos appearing a second time each as generic "social proof" avatars), a direct violation of the template's standing "never reuse the same image anywhere" policy. Caught by re-running the site-wide `uniq -c` duplicate audit immediately after drafting the hero and testimonials sections, before moving on to Categories — consistent with the established practice of auditing after each section rather than only at the very end. **Fix:** removed the redundant avatar-stack from the testimonials section header entirely (kept just the numeric rating, since a second "sample of customers" visual so close to the named testimonial cards below it was redundant content, not just a duplicate-image problem) and sourced 3 fresh, unique customer portraits specifically for the hero's trust badge. **Lesson: decorative "social proof" avatars (trust badges, summary stacks) are exactly where accidental image reuse creeps in, because it's tempting to reach for "a customer photo" generically without checking whether that specific photo is already committed to a named testimonial elsewhere on the same page — treat every avatar/portrait placement as needing its own dedup check, not just product/category photography.**

### Eighth pass — categories.html rebuilt again as a full filterable 72-product catalog
The client's direction reversed course from the fifth pass's "simplify to 6-8 cards" request: this time `categories.html` was asked to become a proper filterable product catalog — a category filter bar (All + the 6 real aisles), exactly 12 items visible at a time in a 4×3 grid, and each item now needing a title, description, HD image, star rating, price, an optional New/Popular/Best-Seller badge, and an explicit CTA button. Read literally, this meant every one of the 6 aisle filters needed its own bank of 12 priced products (72 unique products total), with "All" showing a curated 12-item cross-section rather than everything at once — reconciling "avoid long, cluttered layouts" with "12 items per filter" by ensuring only one 4×3 grid's worth is ever visible at a time, swapped by the filter bar rather than stacked.

**Image sourcing at scale:** rather than sourcing all 72 images from scratch, the ~40 individual product photos removed from `categories.html` and `offers.html` during the fifth pass's simplification (and still sitting unreferenced anywhere on the live site) were re-identified from this session's own history, re-verified as still unused and still HTTP 200, and reused as a 39-image head start — cutting the fresh-sourcing requirement to 33 new photos across the 6 categories. All 72 final image URLs were bulk-verified for HTTP 200 and zero site-wide duplication before being committed to the page.

**Bugs found and fixed during this pass (before sign-off):**
1. **The "All" filter showed all 72 products instead of a curated 12**, because `initCategoryFilter()`'s matching logic was `value === 'all' || cats.indexOf(value) !== -1` — a hard-coded special case that always treats `"all"` as "show everything, unconditionally," a holdover from every earlier use of this function where "All" genuinely meant "no filtering." That assumption broke as soon as "All" needed to mean "show this specific curated subset" instead. Caught immediately by a scripted click-through test that asserted the visible count after every filter button, not just spot-checking one or two. **Fix:** removed the special case entirely — `data-filter-item="produce all"` on 2 items per category makes `"all"` a literal tag like any other, matched the same way as `"produce"` or `"dairy"`. Verified: `all` → 12, and each of the 6 aisle filters → 12, with the 4-column grid confirmed via `getComputedStyle`. **Lesson: a shared filter utility's "match everything" special case is only safe as long as every consumer actually wants that behavior — the moment any one usage needs "all" to mean a specific subset rather than "no filter," the special case must be removed for every consumer, not special-cased further, since a per-page override would silently reintroduce the same bug the next time the function is reused.**
2. **A recycled "Vine-Ripened Tomatoes" photo — already vetted and in production since a much earlier pass — turned out to have a legible, mismatched price sign baked into the shot** ("ORGANIC FRESH CHERRY TOMATOES $4.00 BOX," a different product name and price than the card's own "Vine-Ripened Tomatoes, $2.79/lb"). This photo had passed review before specifically because it was displayed small in a dense 24-card directory; promoted to the #1 "Best Seller" position in a premium 4-column, larger-card catalog, the sign became clearly legible. This is the same "branding risk scales with display size" lesson recorded in the seventh pass, now confirmed as a recurring, not one-off, failure mode for this template — **any image being reused from an earlier, smaller placement must be re-verified at its new size before reuse, every time, not just the first time this lesson was learned.** Replaced with a close-up vine-tomato photo with no signage, re-verified clean, unique, and HTTP 200.
3. Two further candidates were pre-emptively rejected during initial sourcing before ever reaching the page: an olive oil bottle shelf with a real, legible Spanish brand ("Rafael Salgado — Packed in Spain") repeated across every bottle in frame, and an artisan candle with legible product-label text ("Poured by Fi — Calmness") — a small/independent brand rather than a national one, but still real, legible product branding, treated as disqualifying under the same standard regardless of the brand's size or recognizability. Both were swapped for clean alternatives (a spice-spoon shot for the pantry slot, a plain unlit taper candle for the household slot) before either was ever committed to a page, consistent with the project's now-standard fetch-then-Read verification step running *before* an image is written into HTML, not as a post-hoc audit.

### Ninth pass — `categories.html`: "Add" buttons with a toast, richer per-card content, and two more sections
Three changes: replace every product card's "View Details" link (which navigated to `offers.html`) with an "Add" button that behaves like a real add-to-list action — text flips to "Added," stays that way, shows a toast in the top corner, never navigates or reloads; add more per-card substance (an availability line, on top of the rating/price/badge already added in the eighth pass); and bring back page-level content the client felt was missing.

**"Add" button + toast:** all 72 `<a href="offers.html">View Details</a>` links (textually identical, replaced in one `replace_all` pass) became `<button data-add-to-list data-persist>Add</button>`, reusing the same site-wide add-to-list mechanism already powering the Trending section and Offers cards rather than inventing a parallel one. Two small, backward-compatible additions were made to the *shared* `initListAndSteppers()` handler in `main.js`: a new `showToast()` helper (creates a `.toast-root` container lazily on first use, stacks multiple toasts, auto-dismisses each after ~2.9s, mirrors to the top-left under `dir="rtl"`) fires on every `data-add-to-list` click site-wide; and a new opt-in `data-persist` attribute skips the existing 1.4s revert-to-original-icon behavior for buttons that have it. Verified both paths explicitly: a `data-persist` button on `categories.html` stays "Added" past the old 1.4s window, while a plain `data-add-to-list` button on `index.html`'s Trending section (no `data-persist`) still reverts on schedule — confirming the change is additive and didn't regress the carousel/list buttons built in earlier passes.

**Richer cards and page:** added a color-coded availability line to every card (`.availability.in-stock` / `.low-stock` / `.restocked`), varied by badge — Best Seller → "Only a few left," New → "Just restocked," Popular → "Selling fast," everything else → "In Stock" — set programmatically (a Node one-off script matching each badge line to its availability line 10 lines below it, since all 72 cards share the exact same template structure) rather than hand-edited 18 times. Restored the "Why Shop With Us" stat strip (now with animated `data-count-to` counters) and the Offers/Bulk-Order CTA band that existed in the sixth-pass version of this page but were dropped when the page was rebuilt as a 72-product catalog in the eighth pass — their absence, plus the page ending abruptly after the product grid, was almost certainly what read as "too empty." Also added a live `[data-filter-count]` readout under the filter bar ("Showing 12 of 72 products across all aisles" / "Showing all 12 Produce products"), updated by `initCategoryFilter()` on every click, giving the page a small but genuine piece of dynamic, data-driven content rather than static copy.

**No new images this pass** — every change was structural/behavioral (buttons, JS, two restored sections built entirely from existing icon components), so the site-wide image count, dedup, and HTTP-status sweep were re-run only to confirm zero regressions, not because new photography was sourced. **Lesson: not every "make the page richer" request means more photography — data-driven UI (live counts, count-up stats, varied availability states generated from existing badge data) adds genuine content density without touching the image budget or reopening the branding/watermark review surface at all.**

### Tenth pass — `index.html` Shop by Craving + Fresh Picks Gallery redesign, `home-2.html` hero redesign, and a site-wide watermark fix
Three redesign requests plus one significant defect discovered and fixed proactively along the way.

**`?cat=` deep-linking (prerequisite, `main.js`):** `categories.html`'s filter bar previously had no way to be linked into from another page in a pre-filtered state — the old `categories.html#produce`-style anchor links used by the original "Shop by Craving" section were already silently broken (the `id="produce"` etc. anchors were removed from the markup during the eighth-pass 72-product rebuild and never noticed, since a dead in-page anchor fails silently — it just scrolls to the top of the page instead of erroring). `initCategoryFilter()` was refactored to extract a shared `applyFilter(btn, opts)` helper and add `URLSearchParams` support: `categories.html?cat=dairy` now finds and clicks the matching `[data-filter-btn]` on load. The query value is validated against `/^[a-z]+$/` before being interpolated into a `querySelector` attribute-selector string — a raw, unsanitized value could otherwise break out of the selector (a `"` in the query string) and throw an uncaught `DOMException` that would abort the rest of the filter bar's setup. **Lesson: a dead in-page anchor link is a silent failure (no console error, no broken-link tool catches it) — before wiring a new "link into a filtered/scrolled state on another page" feature, explicitly grep the target page for the anchor `id`s the new links assume exist, rather than trusting that a plausible-looking `#hash` still resolves to something.**

**Shop by Craving → asymmetric bento grid:** replaced the 4-card uniform `mood-card` grid (which grouped products by *meal occasion* — "Breakfast Table," "Weeknight Dinner" — only loosely mapped to `categories.html`'s actual 6 aisles) with a new `.craving-grid` CSS-grid-template-areas layout showing all 6 real aisles (Produce, Dairy & Eggs, Bakery, Pantry, Beverages, Household) at genuinely different sizes — one large 2×2 feature tile, two medium tiles, and three small tiles, not a repeated card size — each linking via the new `?cat=` mechanism straight to its pre-filtered `categories.html` view. Reused the existing `.bento-card`/`.bento-overlay`/`.bento-desc`/`.card-cta` component family (previously used only for About's team-photo grid) but added a visible always-on `.card-cta` "Shop [category] →" line plus a hover-revealed `.bento-desc` sentence, since the brief explicitly asked for a "strong CTA button," not just an icon.

**Fresh Picks Gallery → editorial masonry:** replaced the flat 6-column uniform `aspect-square` grid with a second, distinct `.gallery-editorial` CSS-grid-template-areas layout (one wide feature tile, two tall tiles, two more tall tiles, two small tiles — a different area map than the craving grid, so the two redesigned sections don't visually rhyme) with a new `.gallery-tile`/`.gallery-overlay`/`.gallery-caption` component: an always-visible category label + product name, plus a caption sentence that expands in on hover (`max-height` transition). Each tile links into `categories.html?cat=…` as well, giving the gallery a real navigational purpose it didn't have before (it was purely decorative).

**`home-2.html` hero → centered editorial + rotating badge + photo strip:** the brief required this hero to be structurally, not just cosmetically, distinct from `index.html`'s hero. Where Home 1's hero is a full-bleed dark photo background, left-aligned content, a 2-photo offset collage, and a `data-word-cycle` animated headline, the new Home 2 hero is a **light** `--color-bg-alt` background with decorative blobs, **centered** text, a **static** headline (no word-cycle — a deliberately different animation surface, not a repeat of the same mechanic with different words), and a 4-tile horizontal photo strip below the fold-line CTA row with alternating tile heights (`lg:mt-10` on the 1st/4th tiles only) rather than a 2-photo overlapping collage. The previously-built-but-never-used `.spin-badge`/`.spin-badge-wrap` component (a `<textPath>` SVG rotating circular badge, sitting dormant in `style.css` since an earlier, replaced Home 2 concept) was finally put to use here as a "FRESH DAILY · LOCAL ROOTS · EST. 2011 ·" rotating seal next to the CTA buttons — a decorative element that exists nowhere else on the site.
- **Theme bug caught during QA, not by the user:** the photo-strip's caption pill (`.hero-strip-label`) was styled with a fixed white background but `color: rgb(var(--color-ink))` for the text — correct in light mode, but `--color-ink` is a theme variable that flips to a near-white value under `:root[data-theme="dark"]` *and* under a bare `@media (prefers-color-scheme: dark)` match with no `data-theme` attribute present at all (confirmed via a fresh, localStorage-less Puppeteer browser context, which defaulted to invisible near-white-on-white text). The original fix only special-cased `[data-theme="dark"]`, which fixed the explicit-dark-toggle case but not the OS-preference-only case. **Fix:** hardcoded the label to a fixed dark color (`rgb(32 26 20)`) instead of the theme variable, matching the same theme-independent-chip convention already used by `badge-glow` and the bento/gallery overlay text elsewhere on the site (fixed colors for any UI element that sits on top of a photo, since photos don't change with the page theme). **Lesson: theme-variable text color paired with a hardcoded (non-variable) background is only safe if every code path that can set the theme is covered — `[data-theme="dark"]` alone misses the `prefers-color-scheme` fallback path, which a naive "toggle dark mode and look" QA pass won't catch since toggling always sets the attribute explicitly. Test the *zero-attribute* default state in an isolated browser context, not just the explicit toggle states.**

**Watermark defect discovered and fixed (site-wide, not scoped to this task):** while sourcing new photos, the fetch-then-Read verification step revealed that `plus.unsplash.com/premium_photo-*` URLs render with a tiled "Unsplash+" watermark when accessed without a license — invisible to every check this project relies on (HTTP-200 sweep, dedup grep, alt-text review), since the watermark only shows up on the actual decoded pixels. All ~15 `premium_photo-` URLs already live across the site (14 in `categories.html`, 1 testimonial avatar in `index.html`) were confirmed watermarked by spot-checking two of them, then all 15 were replaced with re-sourced, fetch-then-Read-verified `images.unsplash.com/photo-*` (standard, non-Plus) equivalents matching each original subject/alt-text as closely as possible, with two intentional near-substitutions where a truly clean match for the literal subject couldn't be found without a defect (a rolled-towels photo standing in for "laundry detergent bottle," and a 4-candle photo standing in for the described metal-holder single candle) — alt text was rewritten in both cases to accurately describe what the replacement image actually shows, rather than leaving a caption that no longer matched. **Lesson for all future templates: `plus.unsplash.com` (Unsplash+/premium) URLs must be treated as never-safe-to-use without a paid license, full stop — not just "verify like any other image." Restrict all sourcing to `images.unsplash.com/photo-` (standard) URLs going forward, and if a `plus.unsplash.com` URL is ever found already in a project, assume it's watermarked and replace it rather than spot-checking a sample and hoping the rest are fine — the failure mode is invisible to every automated check this project already runs.**

**Image sourcing:** 6 new photos (Shop by Craving), 7 new photos (Fresh Picks Gallery), 4 new photos (Home 2 hero strip), plus 15 replacement photos (watermark fix) — 32 total, every one sourced via `WebFetch` on Unsplash search-results pages and verified via the fetch-then-Read technique before use. Rejection rate stayed consistent with prior passes (roughly 1-in-2 to 1-in-3 candidates rejected for legible brand names/logos on product packaging, foreign-currency price tags, mismatched signage, or — newly — the tiled Plus watermark); the household cleaning-product category in particular required double-digit candidate rounds since minimalist product photography on Unsplash is disproportionately branded mockup/demo content (fake placeholder wordmarks like "Spray Bottle mockups" or "cosmétiques.") or real eco-brand product shots (GOGONANO, Heinz, Campbell's). Final sweep: 114 unique image URLs site-wide, zero duplicates, 100% HTTP 200, zero `plus.unsplash.com` references remaining anywhere in the template.

### Bugs found and fixed during this build (scripted Puppeteer testing before sign-off)
Unlike some earlier templates in this series (whose changelogs record post-launch fixes), this template was interaction-tested with a scripted Puppeteer smoke test — theme/RTL toggles, product filters, quick-view modal, contact-form validation (both empty and valid submission), the repair diagnostic tool, and the About lightbox — before being marked complete. Two real bugs were caught:
1. **`data-specs='["6.1&quot; Super Retina..."]'` broke `JSON.parse` on every product quick-view button.** HTML entity-decodes `&quot;` to a literal `"` *before* JavaScript ever reads the attribute via `getAttribute`, so the JSON parser saw an unescaped quote in the middle of a string value and threw a syntax error. The quick-view modal silently failed to open on every product (no visible error without a `pageerror` listener). **Fix:** since the attribute is single-quoted (`data-specs='...'`), a literal `\"` (backslash + double-quote) can be written directly in the HTML source — the backslash isn't special to the HTML parser, so it passes through unchanged and gives `JSON.parse` the escaped-quote sequence it actually needs. **Lesson: never use `&quot;` (or any HTML entity) to represent a literal quote character inside a JSON-in-HTML-attribute payload — entities decode before JS parses the string, so `\"` (real backslash + real quote, relying on the attribute's own quote-delimiter being different) is the only form that survives both the HTML parser and `JSON.parse` intact.**
2. **The contact form's success message was a sibling of the form's wrapper `<div>`, not a sibling of `<form>` itself**, so `main.js`'s `form.parentElement.querySelector('[data-form-success]')` (the exact lookup pattern documented as the *fix* for this bug class in an earlier template's registry) searched inside the wrong element and silently found nothing — a valid submission hid the form but never revealed the success panel. **Fix:** moved `[data-form-success]` to be a true DOM sibling of `<form>`, inside the same wrapper `<div>`, matching the lookup the JS actually performs. **Lesson: "the success element must be a sibling of `<form>`" is only satisfied by the literal immediate DOM relationship the JS queries against — a success block that's merely visually adjacent (e.g. a sibling of the form's own padded wrapper `<div>`) still breaks the same way; verify the relationship by reading the JS's actual selector, not by eyeballing the rendered layout.**

### Redesign changelog (visual overhaul of a pre-existing, content-complete build)
This template already existed as a fully built, working site (all pages, forms, dark mode, RTL, and content in place) when this pass began. The brief was a **full visual overhaul only** — layout, header/nav, hero, cards, colors, typography, buttons — with content, brand name, business facts, and existing local images left untouched. Notes for future passes of this kind:
1. **Global CSS variables cascade further than page-specific `<style>` blocks.** Swapping the `:root` palette in `style.css` fixed nearly every page automatically, but several pages had inline `<style>` blocks (`home-2.html`'s `.roast-hero`, `.roast-badge`, etc.) with their *own* hardcoded hex/rgba literals copy-pasted from the old palette — those don't inherit from a `:root` change and needed a second, targeted pass.
2. **URL-encoded hex in inline SVG data-URIs is invisible to a literal hex search.** `%239B6A43` (percent-encoded `#9B6A43`) inside a `background-image: url("data:image/svg+xml,...")` string didn't match a plain `#9B6A43` grep/sed pass and had to be swept separately.
3. **Changing a shared component's internal layout direction (e.g. a horizontal menu-card → vertical) breaks any `[dir="rtl"]` override that assumed the old `flex-direction`.** `rtl.css` had `.menu-card { flex-direction: row-reverse; }` from when the card was a horizontal row; after converting it to a vertical "receipt" card, that rule had to be replaced with an RTL-mirrored `clip-path` instead of deleted outright, or the notch would sit on the wrong corner under `dir="rtl"`.
4. **A `position: fixed` navbar that gains a top margin (floating capsule) needs every page's top-of-content clearance bumped by that margin, not just its own height.** Introduced a `--nav-gap` variable and added it to `.hero`, `.page-header`, and the Home-2-specific `.roast-hero` — missing even one of these left content tucked up under the floating pill on that one page.
5. **`clip-path` on a card silhouette clips its own `box-shadow` at the same polygon**, unlike `border-radius`. Visually this reads fine for a "ticket corner" (the shadow just cuts off cleanly at the diagonal instead of following a rounded corner) but it's worth knowing going in — it is not a bug to chase.
6. **Verification order that worked well for a redesign-of-an-existing-site (vs. a from-scratch build):** grep every literal old-hex/rgba occurrence site-wide *before* touching component CSS (caught 56 occurrences across 19 files, including the encoded-SVG case above), then restyle shared components (cascades to every page for free), then rebuild the two homepage heroes by hand (the only genuinely bespoke markup), then Playwright-screenshot every page in light/dark/RTL/mobile to catch what a visual pass alone misses — this caught zero real bugs on the first pass, but is what confirmed there were none, including a body-clipped 4px sub-pixel rounding "overflow" on mobile that measured as `scrollWidth > innerWidth` but was never visible or scrollable (`body { overflow-x: hidden }` was already the site's own long-standing safety net).
7. **A generic "Home" dropdown containing Home 1/Home 2 sub-items is exactly what the master prompt's mandatory nav rule forbids** ("Show Home 1 and Home 2 directly in the main navigation. Do not place the remaining navigation items inside a generic dropdown.") — the first pass of this redesign left the pre-existing site's `Home ▾ → Home v1 / Home v2` dropdown structurally untouched while restyling everything else, and it was only caught on a follow-up request. Fixed by flattening it into two direct `<li>` links ("Home 1" / "Home 2", exact wording from the rule) on all 10 pages that carry the shared navbar, with the `active` class moved onto whichever of the two is the current page. **Lesson: when redesigning an existing site's *visual* system, still re-check its nav structure against the master prompt's structural rules — a scope of "colors/layout/cards" doesn't exempt already-present structural violations from being fixed.**
8. **`clip-path` on a parent with `overflow: hidden` clips *all* descendants to that shape, including absolutely-positioned children meant to intentionally spill outside it.** Home 2's floating stat card (`.roast-float-stat`, `left: -140px`) was originally a child of `.roast-hero-media`, which also carried the notch `clip-path` + `overflow: hidden` for the image. The card's left portion — and on some viewport widths, its leftmost stat entirely — was silently clipped off, invisible in a quick look but caught immediately by a full-page screenshot. **Fix: split the masking from the positioning** — the `clip-path`+`overflow:hidden` now lives on a new inner `.roast-media-mask` wrapper around just the `<img>`, while `.roast-hero-media` itself stays `overflow: visible` so the sibling floating card can render outside the image's bounds. **Lesson: never put a clip-path/overflow mask on the same element that also hosts an intentionally-overflowing absolutely-positioned child — always give the mask its own dedicated wrapper.**

### Second follow-up round: content trims, per-page hero variety, and a nav reversal

9. **Removed the "Everything Made with Care" Menu Categories section from `index.html` entirely** (the section had already been renamed to "Pick Your Pour" as a lighter first attempt — the follow-up request was to drop the section outright, not just rename it). ### Third follow-up round: two genuine interaction/layout bugs caught by actually driving the controls, not just inspecting state

25. **Found a real, separate RTL bug while investigating the above: dash-separated time ranges visually reverse their own internal order under `dir="rtl"`.** `7:00 – 19:00` (correct in the HTML source) was rendering as `19:00 – 7:00` on screen — not a layout-mirroring issue but the Unicode Bidi Algorithm itself: a run of purely "weak"/neutral characters (digits, colon, space, en-dash) with no strong directional character, sitting inside an RTL paragraph with no isolating boundary, gets its own internal segments reordered right-to-left. Fixed by isolating each of these runs from the ambient RTL context: `.hours-row .time { direction: ltr; unicode-bidi: isolate; }` in `style.css` (covers both pages' hours widgets in one rule), and `dir="ltr"` added directly to the specific `<span>`/`<a>` elements carrying the footer hours line and phone number (bulk-applied across all 10 shared-footer pages plus the two contact-only lines). **Lesson: any hardcoded LTR content — number ranges, phone numbers, dates, code/SKU strings — embedded inside a page that supports `dir="rtl"` needs its own directional isolation (`dir="ltr"` or `unicode-bidi: isolate`); relying on "it's just numbers, bidi won't touch it" is exactly the assumption that produces this bug, and it will not show up in a layout-level RTL check (nav mirrors, cards flip, alignment is correct) — only reading the actual rendered digits catches it.**
26. **Item 24's "confirmed working" verdict was wrong — the real bug was a double-reversed `flex-direction`, and it affected far more than the navbar.** User re-reported "nav menus not working RTL/LTR" after item 24 closed it out. Root cause: `rtl.css` had `[dir="rtl"] .navbar-inner/.navbar-brand/.nav-menu/.navbar-actions { flex-direction: row-reverse; }` (plus ~20 more rules on the same pattern: `.hero-stats`, `.category-link`, `.blog-meta`, `.read-more`, `.testimonial-author`, `.faq-question`, `.reserve-steps`/`.reserve-step`, `.side-post`, `.btn`, `.breadcrumb`, `.pricing-features li`, `.footer-contact-item`, `.footer-socials`, `.footer-bottom`, `.footer-bottom-links`, and the admin-dashboard's `.sidebar-link`/`.sidebar-footer`/`.topbar`/`.topbar-right`/`.donut-legend-item`). Every one of these is a flex container whose *only* direction rule was already `row` (the CSS default, unset) — but `dir="rtl"` on `<html>` also sets the UA-level `direction: rtl`, which every descendant inherits, and **a flex container's own `flex-direction: row` already auto-mirrors its main axis when its `direction` is `rtl`** (main-start becomes the right side). Layering an explicit `row-reverse` on top of that inherited auto-mirror is a double negative: two reversals cancel out, so the container renders in the *exact same physical left-to-right order as plain LTR* — which is precisely why the navbar "looked unchanged" after toggling RTL (only the `.dropdown-menu { right:0 }` position rule visibly moved, which is why the user specifically said "Home only changes, remaining menus are not"). Item 24's test only checked `getComputedStyle().flexDirection === 'row-reverse'` (the property's cascade value) and that `dir` flipped to `"rtl"` — neither check catches a double-reversal, because both individually look "correct"; only comparing actual rendered x-coordinates (or a real screenshot) between LTR and RTL reveals it. **Fixed by deleting every `flex-direction: row-reverse` override in `rtl.css` and letting the inherited `direction: rtl` do the mirroring on its own** — verified afterward with a Playwright check of each nav item's bounding-box x-coordinate (LTR: increasing left→right per DOM order; RTL: decreasing, i.e. correctly mirrored) plus visual screenshots of the navbar+dropdown, hero stats, footer (columns and the bottom copyright/links row), testimonials, and mobile drawer, all now genuinely mirroring instead of silently not. **Lesson: `flex-direction: row-reverse` and an inherited `direction: rtl` compose, they don't stack independently — if a flex container already inherits `rtl` from `dir="rtl"` on `<html>`, it needs *no* `flex-direction` override at all to mirror; adding `row-reverse` "to be sure" is the bug. And a computed-style assertion (`flexDirection === 'row-reverse'`) proves the CSS rule applied, not that the layout is visually mirrored — those are different claims once inherited `direction` is in play.**

### Build notes for future passes of this kind
1. **A tool that appears to write files can silently be sandboxed away from the real disk.** Early in this build, `cp -r`/`rm -rf` run through the Bash tool completed without error and were even readable back through the same tool afterward, but a native process (Node, PowerShell) looking at the same path saw none of it — the project folder was still empty. The harness's own `Write`/`Edit` tools and `PowerShell` both reliably hit the real filesystem; a `Bash` `cp`/`mv`/`rm` did not, in this environment. **Lesson: after any bulk file-management operation done through a shell tool (not a dedicated Write/Edit call), verify the result through a second, independent tool (a different shell, or the harness's native file tool) before trusting it — a same-tool read-back is not independent verification.**
2. **A visually-hidden "skip to content" link positioned via `left:-999px` overflows the document specifically under `dir="rtl"`, not under `dir="ltr"`, because RTL's natural overflow direction is negative-x** — the same offset is silently ignored for LTR scroll purposes but gets pulled into the root element's scrollable range in RTL, inflating `documentElement.scrollWidth` by exactly the offset amount and shifting the entire visible viewport in a screenshot/manual scroll check. Fixed by switching to the clip-path "visually hidden, `1px×1px`, reset on `:focus`" technique, which never leaves the layout viewport regardless of direction. **Lesson: any classic negative-offset "visually hidden" technique (`left:-9999px` and similar) needs an RTL-mode overflow check specifically — an LTR-only overflow check (even at multiple breakpoints) will not catch it, because the bug is direction-dependent, not width-dependent.**
3. **A decorative connector line built with `::before{left:-50%}` and suppressed only on `:first-child` breaks in RTL** because flex row layout under `direction:rtl` visually reverses item order while DOM order (and therefore `:first-child`/`:last-child`) stays the same — the DOM-last item becomes visually leftmost and draws its (still physically-`left`) connector further left, past the viewport edge, while the DOM-first item (now visually rightmost, correctly still suppressed) is fine. Fixed with `[dir="rtl"] .step::before{left:auto;right:-50%}`. **Lesson: any component that hides a decorative pseudo-element on `:first-child` to mark "the start of a sequence" needs a mirrored rule for RTL, because "the start" moves to the opposite physical edge while `:first-child` does not.**
4. **Assumed stock-photo content (from ID-pattern familiarity rather than an actual look) was wrong often enough to be the dominant source of defects in this build, not the exception.** A hero image assumed to be a generic "warm bookshop interior" turned out to be a tight macro shot of a real, identifiable, currently-in-print book with its full title legible (a commercial-license risk directly matching the T13 toy-store IP lesson, just with a book cover instead of a licensed character). Other assumed-safe picks turned out on inspection to be: a stack of real, legible business-book covers; a photo of literal cash money; a real classroom scene (used where "bookstore interior" was needed); a single-portrait ID that was actually a five-person classroom photo. None of these were flagged by the normal verification pass (HTTP 200 checks, link checks, console-error checks) because they are content-correctness problems, not technical ones. **Lesson: for a template whose stock imagery is sourced by ID rather than hand-picked from a visual gallery, budget a dedicated pass that actually downloads and visually previews every candidate photo before committing to its use and its `alt` text — treat "the URL returns 200" and "the photo shows what I assume it shows" as two completely independent facts requiring two completely independent checks.**
5. **A full-page Playwright screenshot taken shortly after `networkidle` will show scroll-triggered reveal animations as still-hidden (`opacity:0`) for content below the first viewport**, reading as a rendering bug (elements "missing," large blank gaps) when the underlying DOM/CSS is completely correct — confirmed by direct `getBoundingClientRect`/`getComputedStyle` inspection showing every element present, correctly sized, and correctly positioned, just pre-reveal. **Lesson: when a full-page screenshot shows implausible blank gaps on a site using scroll-triggered reveal classes, verify via direct DOM/style inspection (or a manual scroll-through before capture) before concluding there's a layout bug — the screenshot's capture timing, not the page, is often the actual variable.**
6. **A follow-up request to "add images, not just colors" to card components that were deliberately built as flat CSS-gradient blocks (to avoid needing real book-cover art for invented, non-existent titles) was satisfied by layering a genre-mapped photograph *underneath* the existing gradient as a semi-transparent tint**, not by replacing the gradient system outright — this kept the "same shelf" cross-page color-consistency the cards were designed around while adding the requested photographic richness, and reused the same six pre-vetted (IP-safe, no-legible-text) genre photographs already established for hero/band imagery rather than sourcing 20+ new individual images for 20+ invented books. **Lesson: "add images" to a color-coded component system doesn't have to mean abandoning the color coding — compositing a photo behind the existing semantic gradient (`linear-gradient(rgba(...),rgba(...)), url(...)`) preserves the coding while adding texture, and is far cheaper than sourcing/vetting one unique photo per data item.**

7. **A follow-up request to fold "Home 1 / Home 2" into a single "Home" dropdown directly contradicted this series' own master-prompt rule ("show Home 1 and Home 2 directly in nav, not in a dropdown").** Treated as an explicit, scoped override — the user's direct instruction in the moment outranks a standing default from the master prompt — and implemented as a hover-or-click dropdown (`:focus-within` for keyboard, a `.open` class for touch/click, outside-click and Escape to close) rather than silently refusing or re-litigating the original rule. **Lesson: a standing rule from the master prompt is a default, not a constraint the user can't override for their own template — apply it unless and until the user gives a specific, scoped instruction to do otherwise, then follow the instruction.**
8. **The genre-color-mapped photo-tint system from note 6 (one shared photo per genre, reused across every book in that genre) was explicitly rejected in a later request ("don't use same images, use unique images") — "one photo per genre" and "unique images" are different, incompatible specs, and satisfying the master prompt's own "avoid repeating the same image" rule required abandoning the cheaper shared-photo approach entirely.** Fixed by sourcing 26 individually-vetted, distinct photographs (one per invented book, matched loosely to its title/mood rather than strictly to genre) via a contact-sheet review (composing many candidate thumbnails into one HTML grid and screenshotting it in one pass, rather than one-at-a-time preview calls) to keep the visual-verification lesson from note 4 affordable at 26-image scale. **Lesson: "add images" and "add *unique* images" are different requests with different minimum costs — don't assume a cheaper shared-asset solution satisfies a request for per-item uniqueness just because it technically added photography; and when a vetting pass needs to scale to dozens of candidates, batch the previews into one composite image instead of one tool call per image.**
9. **A request to "show selected book details" surfaced that every "Details" link on the entire site pointed to the same static `book-details.html`, which always rendered one hardcoded book (Greywater) regardless of which card was clicked** — a real functional defect that had shipped silently because every automated check up to that point (link-exists, page-loads-200, no-console-errors) only verifies that *a* page loads, never that it loads the *right content* for the link that was clicked. Fixed properly for a static-only site (no backend, no build step) by converting the single detail page into a query-string-driven template (`book-details.html?id=slug`) backed by one `assets/js/books-data.js` object of all 26 books, rather than hand-duplicating 26 nearly-identical HTML files — the latter would have violated this series' own "don't repeat large HTML blocks unnecessarily" rule and made every future copy-edit a 26-file chore. **Lesson: "every card links to a details page" is not the same claim as "every card links to *its own* details page" — a link-integrity check (does the href resolve, does the page 200) cannot catch "right page, wrong content," because that failure mode requires comparing the clicked item's identity against what actually rendered, not just confirming *a* render happened. For a static site needing N near-identical detail pages, prefer one query-param-driven template over N duplicated files.**
10. **A request to "remove image shade" on book covers meant something different from note 6/8's photo-tint work: not the semi-transparent color wash over the *whole* photo (already partly addressed), but specifically that the wash was still muting the photography enough to read as "shaded" rather than "photographic."** Fixed by dropping the full-cover color tint entirely and replacing it with a `::before` pseudo-element bottom-anchored gradient (`rgba(10,7,5,.82)` at the base fading to transparent by ~70% up), scoped only to the area needed for white title-text contrast — the same technique already used elsewhere in this site's own `.journal-feature::before` for photo captions, just not yet applied to book covers. **Lesson: "remove the shade" on a photo-plus-text card usually means "let the photo read clearly," not "remove all legibility treatment" — a bottom-anchored scrim sized to the text is the standard middle ground, and this template already had the pattern in use elsewhere; check for an existing sibling solution before inventing a new one.**
11. **A request to "redesign books.html" was made three times before landing — two attempts (adding sections, then adding a featured-strip + hero texture) were reasonable improvements that still missed the actual ask, and continuing to guess a fourth time risked burning as much effort as the previous three combined for another possible miss.** The third attempt stopped and asked a single scoped clarifying question with concrete options instead of iterating again blind; the answer ("doesn't look modern enough" — wants filter sidebar, sort, grid/list toggle, pagination) was a different category of change (information architecture) from what had been tried (content density, imagery), which explains why volume/content additions hadn't resolved it. **Lesson: if a redesign request repeats after a genuine, substantive attempt already shipped, the next default shouldn't be "try a bigger version of the same kind of change" — it's a signal the mental model of the *category* of fix is probably wrong, and one clarifying question is cheaper than another full guess.**

12. **A pagination request ("add pagination" after a "3×2, remaining" instruction) was satisfied with real numbered pages (1/2/3 + prev/next, each replacing the visible set), not another "Load More" button** — the two are different UX contracts (accumulate-in-place vs. replace-and-jump), and the user's phrasing ("remaining add pagination") specifically implied the *rest* of the catalog should live behind page controls rather than an ever-growing single page. **Lesson: "pagination" and "load more" are not interchangeable even though both solve "too many items for one screen" — implement the one named, and if a prior "load more" pattern exists on the same control, it should be replaced outright rather than layered.**
13. **A hero text-overlap bug (`h1` visually colliding with the ticker strip below it) traced back to a structural mistake that had shipped silently since the original build: `.hero-ticker` was a sibling *inside* the same flex container as the hero's text column, and `display:flex` defaults to `flex-direction:row`, not `column`.** With `align-items:center` and no explicit direction, the text block and the ticker were being laid out as two side-by-side row items, each independently vertically centered — which visually reads as overlap once the text block is tall enough (worsened separately by an oversized `clamp()` headline forcing 5–6 line-wraps in a narrow column). Confirmed via direct `getBoundingClientRect` measurement of both elements (their vertical centers matched the "independently centered flex row item" math exactly), not by eyeballing the screenshot. Fixed by adding `flex-direction: column` (the missing declaration) and separately taming the headline's `clamp()` range and line count. **Lesson: a flex container with more than one in-flow child and no explicit `flex-direction` silently defaults to row — if the visual intent is "stacked," that declaration is not optional, and a "these two elements are overlapping" bug is worth measuring both elements' actual boxes before assuming it's a spacing/z-index issue.**
14. **A "the two columns should have the same height" complaint (New Arrivals spotlight: image+text stage vs. the thumbnail rail) traced to `align-items: start` on the parent grid** — CSS Grid's default is `stretch`, but it had been explicitly overridden to `start`, which stops both grid-item columns from matching each other's height and instead lets each size to its own content. Fixed by restoring `align-items: stretch` on the parent and adding `height: 100%` down through the slide/cover-block chain so the now-stretched column's image actually fills it (rather than stretching the empty box while the image stayed at its old fixed height). **Lesson: "two side-by-side elements don't match height" in a CSS Grid layout is almost always an `align-items` question first — check for an explicit non-default override before adding manual height rules.**
15. **A repeated "redesign, doesn't look good" complaint on a section (Staff Picks) was resolved in one pass this time, not three, by asking a single scoped multiple-choice question before touching code** — directly applying the lesson from the Books-page redesign cycle earlier in this file. The chosen fix (static 3×2 grid instead of a horizontal scroll shelf) was a structural change the two prior "vague redesign" guesses on Books had never needed, confirming that "layout structure" complaints are frequently about the *containment/scroll mechanic*, not the card content — a detail easy to miss when the most recent edit was to the card's content (staff attribution) rather than its container. **Lesson: when a "not good, redesign" complaint follows shortly after a content-only change, the mechanic (scroll shelf vs. grid vs. list) is a more likely culprit than the content, precisely because content was what just changed and evidently wasn't the complaint.**
16. **An IP-safety photo swap identified during an early audit pass (a travel-guidebook shelf with legible real covers, flagged as risky for the Home 1 community band) was never actually applied — the audit correctly identified the problem and stated an intent to fix it, but the corresponding file edit was never made, and the risky photo shipped for several more rounds of unrelated work before a fresh screenshot surfaced it again by chance.** **Lesson: identifying a fix during an audit and stating the intent to make it are not the same as making it — an audit pass should end with either the edit applied immediately or a tracked, checked-off item, not a narrative "I'll swap this" that has no enforcement mechanism; treat every "risky, will fix" audit finding as incomplete work until independently re-verified, not just remembered.**
17. **A "remove [X] section, add any image or text, use best layout, don't use cards" instruction was satisfied by replacing a per-book related-books card row with a single dynamic `.band-photo` (full-bleed genre-mood photograph + editorial pull-text + one CTA), reusing this template's own established non-card image-band component rather than inventing a new one.** The band's content (photo, heading, body text, CTA target) is looked up per-genre from a small in-script object and swapped via the same `?id=`-driven render pass already built for the rest of the page, so it stays accurate to whichever book is loaded without needing per-book unique copy. **Lesson: "don't use cards" doesn't require a novel component — check whether the template already has a non-card content pattern (here, the photo-band used elsewhere for editorial/community messaging) before designing a new one from scratch.**
18. **Three same-turn requests to add "one more section, different layout and structure" to three different pages (Genres, Events, Journal) were deliberately fulfilled with three structurally distinct patterns — a collapsible FAQ accordion, a 3-column testimonial quote-grid, and a 2-column photo+bio feature split — rather than the same "just another card row" pattern three times,** even though all three pages already had card-grid-shaped content elsewhere. **Lesson: when one instruction asks for the same kind of addition across multiple pages in a single sentence, satisfying it well means selecting a different existing component per page (matching what that specific page is missing structurally), not batch-applying one convenient pattern to all of them.**
19. **Redesigning the Staff Picks section's markup (shelf → grid) orphaned an anchor link on a different page (`genres.html` linked to `index.html#staffShelf`, an `id` that no longer existed after the rewrite) — caught only by a proactive same-session re-check of that specific link, not by any automated test, since a dangling `#hash` fragment doesn't produce an HTTP error or a broken-link warning of any kind.** Fixed by giving the replacement section a durable `id="staff-picks"` and updating the one cross-page reference. **Lesson: renaming or removing an element `id` that a scroll-target anchor depends on is a cross-file dependency exactly like a renamed file — grep the whole project for the old `id` (not just the file being edited) before considering an element-identity change complete, since `#fragment` links fail completely silently.**

20. **A request to "add one more section" to Book Details was satisfied without writing any new per-book copy, by re-presenting content that already existed (`desc2`, previously a second paragraph inside the Description tab) as a separately-styled `.staff-note` callout** (gold left-border box, small staff-initial avatar colored/assigned by a genre→bookseller lookup matching the real staff bios established on the About page) **and removing it from the tab so the content isn't duplicated in two places at once.** **Lesson: "add a section" doesn't always mean "write new content" — check whether an existing field is already sitting underused in a denser format (a second tab paragraph, a truncated list item) before drafting anything new; re-presenting it as its own styled block can satisfy the request at zero content cost.**
